# Прогноз пассажиропотока трамваев Москвы

Веб-сервис прогнозирует посадки (успешные валидации) на 10 трамвайных маршрутах по часам и показывает их на графиках и карте.
Прогноз - модель команды (`model/tram_model`) на 01.11–31.12.2025. Её WAPE-score на платформе хакатона выше 0.89. Для сравнения на сайте есть встроенный профильный baseline.
Можно загрузить свой файл сырых валидаций и сравнить факт с прогнозом, выгрузить результаты в CSV/XLSX.

## Запуск

```bash
docker compose up --build
```

- дашборд - http://localhost:3000
- API и Swagger - http://localhost:3000/api/docs
- масштабирование API - `docker compose up --scale api=3`

При старте worker за несколько секунд строит прогноз, дашборд подхватывает его сам.

История посадок и справочник остановок в git не хранятся (`*.csv` и `*.xlsx` в `.gitignore`). Перед первым запуском
положите файлы из архива хакатона:

- `labels/labels_day_train.csv` и `labels/labels_day_test.csv` → `data/history/`;
- `spravochniki/Хакатон_справочники_трамвай_10_маршрутов.xlsx` → `data/reference/`.

Без них сайт показывает прогноз модели, но без режима «Baseline» и без остановок маршрутов 1, 5, 7, 11, 12 на карте.
Вместо labels можно положить сырые `train.csv` и `test.csv` в `data/incoming/`: worker сам посчитает посадки по часам,
но обработка 10 ГБ займёт несколько минут.

## Что есть на сайте

- **Источник данных:** «Модель», «Baseline» (профильный прогноз по истории, не ML) или «Файл» - переключатель меняет все блоки сразу.
- **График и сводка:** горизонт день / месяц / год, фильтры по маршруту, остановке, часам и шагу времени; пики и разбивка по типу дня.
- **Карта:** загрузка остановок по часам, «Динамика за сутки», режим «Сейчас»; линии маршрутов идут по рельсам.
- **Файл валидаций:** CSV/XLSX в формате сырых валидаций хакатона (кнопка «Шаблон»). Сайт считает посадки по часам и показывает
  факт из файла и прогноз модели на одной шкале; файл результата - `route;date;hour;fact;prediction;source;error`.
- **Выгрузка** текущего графика в CSV и XLSX.

## Применение

Прогноз рассчитан на планирование работы трамвая: выпуск вагонов, расписание, компенсационный транспорт.

- **Выпуск вагонов по часам.** Прогноз маршрут × час показывает, когда нужен максимум вагонов на линии. В будни два пика,
  8 и 18 ч, в выходные один горб 12–16 ч. Главный эффект - на маршрутах 17, 12, 11 и 7: на них 64 % посадок ноября–декабря.
- **Праздники и особые дни.** 03–04.11 модель ждёт ≈ 0.48 от обычного будня (0.32–0.60 по маршрутам), 31.12 - ≈ 0.41.
  В эти дни хватит выпуска по графику выходного дня. С 20:00 31.12 проезд бесплатный, валидаций не будет.
  Рабочая суббота 01.11 - почти как будний день (× 0.92).
- **Ремонты и компенсационный транспорт.** По выходным в декабре, после ремонта путей, модель ждёт на маршруте 50
  ≈ 10 тыс. посадок в день. Примерно столько пассажиров в выходной приходилось перевозить автобусами и трамваем 37,
  пока маршрут был закрыт.
- **Загрузка участков.** Карта по часам показывает остановки с наибольшей нагрузкой - кандидаты на укороченные рейсы
  и дополнительные вагоны. Оценка по остановкам расчётная, см. «Область применимости».
- **Контроль прогноза.** Свежие валидации загружаются через «Файл», сайт показывает отклонение факта от прогноза в процентах.
  Устойчивое отклонение - сигнал пересчитать уровень и пересобрать модель.

Наполняемость салона прогноз не даёт: в данных есть посадки, но нет высадок. О переполнении можно судить только косвенно,
по числу посадок в час.

## Как устроено

| Сервис | Стек | Роль |
|---|---|---|
| `worker` | pandas, pyarrow | Пайплайн по расписанию: приём валидаций → история → геопривязка → прогноз модели → публикация snapshot |
| `api` | FastAPI, numpy | Держит опубликованный прогноз в памяти, перечитывает новую версию без перезапуска |
| `frontend` | React, TypeScript, Tailwind, Recharts, MapLibre | Дашборд; nginx раздаёт статику и проксирует `/api/` |
| `postgres` | PostgreSQL 16 | Копия истории, прогноза, справочников и журнала прогонов |

API читает только файлы snapshot, поэтому не хранит состояния и масштабируется горизонтально.

## Данные и модель

- `data/history/` - почасовая история посадок (январь–октябрь 2025), `data/incoming/` - новые сырые валидации для пайплайна.
- `data/reference/` - справочник маршрутов и остановок и выгрузка OpenStreetMap (`osm_tram.geojson`: остановки маршрутов
  17, 25, 26, 28, 50 и трассы по рельсам). Обновить выгрузку: `python -m worker osm`.
- Модель подключается через адаптер и не пересобирается сервисом: по умолчанию читается готовый
  `model/tram_model/artifacts/forecast.csv`. Другие способы подключения - в [model/README.md](model/README.md).
- Модель: прогноз = уровень маршрута × форма. Уровень - средний обычный будний день маршрута за последние 4 недели октября.
  Форма - доля от уровня в этот час этого дня, среднее трёх моделей: профиля по медианам, 9 LightGBM и CatBoost.
  Подробно - в [model/tram_model/README.md](model/tram_model/README.md).

Основные настройки worker (переменные окружения):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MODEL_MODE` | `file` | `file` - готовый файл прогноза, `plugin` - `model/predictor.py`, `baseline` - без модели |
| `MODEL_FALLBACK` | `baseline` | Чем заполнять дни вне прогноза модели (`none` - ничем) |
| `FORECAST_END` | конец файла модели | Продлить период прогноза baseline'ом |
| `PIPELINE_INTERVAL_MIN` | `60` | Период плановых прогонов (плюс прогон при изменении входных файлов) |
| `DATABASE_URL` | - | PostgreSQL; без неё пайплайн работает только с файлами |

## Внешние факторы

Эффект каждого фактора проверен на истории январь–октябрь 2025. Исключение - события без аналогов в истории.

| Фактор | Источник | Как учтён в модели | Эффект в данных |
|---|---|---|---|
| Производственный календарь РФ: праздники, переносы, рабочая суббота 01.11, сокращённые дни | [КонсультантПлюс, 2025](https://www.consultant.ru/law/ref/calendar/proizvodstvennye/2025/); для baseline после 31.12.2025 - [2026](https://www.consultant.ru/law/ref/calendar/proizvodstvennye/2026/) | Признаки дня: праздник, длина праздничного блока и место в нём, день до и после, рабочая суббота как пятница (`tram/calendar.py`) | Праздник в будний день - 0.37–0.52 от обычного такого же дня недели, 01.01 - 0.23 |
| Сезонность: световой день | Расчёт по широте Москвы (55.75°) через склонение Солнца, `tram/calendar.py` | Признак `daylight_c`; июль–август в обучении с весом 0.3 | Летом дневной профиль заметно отличается от остального года, днём ездят меньше |
| Ремонт путей в Протопоповском пер.: с 06.09.2025 по выходным маршрут 50 отменён, 7 укорочен, до конца осени | [Агентство «Москва», 05.09.2025](https://www.mskagency.ru/materials/3506273), [«Восточный округ», 12.09.2025](https://newsvostok.ru/dlya-tramvaev-7-i-50-izmeneniya-po-vyhodnym-budut-dejstvovat-do-kontsa-oseni/) | Признаки режима `weekend_closed` (50) и `weekend_reduced` (7) по 30.11; с декабря - обычные выходные | Выходной / будний: у 50 - 0.40 в марте–июне и 0.03 в сентябре–октябре, у 7 - 0.56 и 0.35 |
| Новый маршрут 5 «Рижская» - Белорусский вокзал с 16.12.2025 | [Московский метрополитен, 16.12.2025](https://mosmetro.ru/news/details/8515) | До 16.12 прогноз 0, с 16.12 - суточный профиль маршрутов 17 и 25 × 5 500 посадок в будний день | В истории маршрута нет, уровень экспертный |
| Бесплатный проезд в новогоднюю ночь, 20:00 31.12 - 06:00 01.01 | [mos.ru, 31.12.2025](https://www.mos.ru/news/item/164558073/) | С 20:00 31.12 прогноз 0: при бесплатном проезде валидаций нет | 01.01.2025 в 00–03 ч - 0 валидаций (в обычный день в 00 ч около 460), в 05 ч - 25 против 390–590 |

Погода и дорожный трафик не используются.

## Область применимости

**Где прогноз валиден**

- Маршруты 1, 5, 7, 11, 12, 17, 25, 26, 28, 50, период 01.11–31.12.2025, шаг - час.
- Целевая величина - успешные валидации, а не пассажиры в салоне: бесплатный проезд и поездки без оплаты в неё не попадают.
- Точнее всего прогноз маршрута по часам и его суммы за день и месяц.
- Прогноз по остановке - расчётная доля от маршрута: в валидациях нет остановки, только депо. Посадки убывают к конечной,
  направления делят поток поровну. Проверить эти доли на данных нельзя.
- Горизонт «год»: модель покрывает только ноябрь–декабрь 2025. Если задать `FORECAST_END`, остальные месяцы достраивает
  baseline (профиль последних 5 недель × сезонный индекс, не ML). Это качественная оценка, на графике такие столбцы серые.

**От чего зависит прогноз**

- От уровня октября. Ошибка уровня переходит в прогноз один в один; на бэктесте основная ошибка - именно уровень, а не форма.
- От календаря и режимов маршрутов. Модель не выводит их из данных, они заданы в `tram/settings.py`.
- Поправки уровня по маршрутам и месяцам `ROUTE_MONTH_K` (0.96–1.00) и `DAY_K` для 01.11 подобраны по проверкам на платформе,
  то есть под ноябрь–декабрь 2025.

**Как перенести на новый период**

1. Подготовить почасовую историю в формате labels (`route;date;hour;boardings`, файлы `labels_day_train.csv` и `labels_day_test.csv`).
2. В `model/tram_model/tram/settings.py` обновить календарь нового периода (`HOLIDAYS`, `WORKING_WEEKENDS`, `SHORT_DAYS`,
   `NEW_YEAR`), `HORIZON`, `HISTORY_END`, режимы маршрутов `REGIMES` по новостям о ремонтах и события (`ROUTE5_*`,
   `BRIDGE_DAYS`, `FREE_NIGHT_FROM`). `ROUTE_MONTH_K` и `DAY_K` сбросить в 1. Расширить диапазон календаря в `tram/calendar.py`.
3. Пересобрать из `model/tram_model`: `python -m tram.forecast --labels <папка>`. Worker подхватит новый `artifacts/forecast.csv` сам.

**Как добавить маршрут**

- Модель общая для всех маршрутов, но номер маршрута - её признак, а уровень и доли часов считаются по истории маршрута.
  Нужна история хотя бы за 4–5 недель обычной работы, после этого модель пересобирается.
- Без истории - как маршрут 5: профиль похожих маршрутов × экспертный уровень.

**Ограничения**

- Маршрут 5: истории нет, прогноз с 16.12 построен по аналогам с экспертным уровнем. Это наименее надёжная часть прогноза.
- 29–31.12: аналогов в истории нет, она начинается 01.01.2025. Снижение 29–30.12 (× 0.90) - экспертное допущение.
- Резкие события вне списка выше - снегопады, аварии, новые перекрытия - прогноз не видит.

## API

Ответы - JSON, ошибки - `{"error": {"code", "message"}}`. Полное описание параметров - в Swagger.

| Метод | Назначение |
|---|---|
| `GET /api/forecast`, `/api/summary` | Прогноз и сводка: `horizon`, `date`, `route`, `stop_id`, `hour_from/to`, `granularity`, `source` |
| `GET /api/map`, `/api/stops`, `/api/routes` | Нагрузка остановок на карте, остановки и линии, список маршрутов |
| `GET /api/export/csv`, `/api/export/xlsx` | Выгрузка с теми же параметрами |
| `GET /api/predict`, `POST /api/predict/batch` | Прогноз для одного ключа или файла ключей `route;date;hour` |
| `POST /api/datasets` | Загрузить файл сырых валидаций → `source=file:<id>` для графиков и карты |
| `GET /api/meta`, `/health`, `/ready` | Версия и период прогноза, статус пайплайна, проверки живости |

```bash
curl "http://localhost:3000/api/forecast?horizon=day&date=2025-11-10&route=17"
curl -OJ "http://localhost:3000/api/export/xlsx?horizon=month&route=7"
curl --data-binary @test.csv -H "Content-Type: text/csv" "http://localhost:3000/api/datasets?filename=test.csv"
```

## Производительность

Замер k6 (`loadtest/k6.js`) постоянной интенсивностью по 60 с на ступень. Смесь запросов дашборда со случайными маршрутами, датами и горизонтами:
- `/api/forecast` - ~60 %, включая запросы по остановке и интервалу часов;
- `/api/summary` - 15 %;
- `/api/map` - 15 %;
- `/api/predict` - 10 %.

Запуск:

```bash
sh loadtest/run.sh                          # напрямую на api:8000, ступени 200 400 800 RPS
sh loadtest/run.sh http://api:8000 300 600  # свои ступени
sh loadtest/run.sh http://frontend:80 400   # через nginx
```

Результаты сохраняются в `loadtest/results/`: вывод k6 и `docker stats` контейнера api раз в секунду.

**Стенд:**
- хост - Windows 10, 8 CPU, 8 ГБ RAM, Docker Desktop;
- контейнер `api` - лимит 2 vCPU / 2 ГБ (`cpus: 2`, `mem_limit: 2g`), uvicorn с `WEB_CONCURRENCY=2`;
- k6 работает на том же хосте и конкурирует с api за CPU, поэтому цифры - оценка снизу.

### Один контейнер api, напрямую (2 воркера uvicorn)

| Нагрузка | Факт RPS | p50 | p95 | p99 | Ошибки | CPU api (100 % = 1 vCPU) | RAM api |
|---|---|---|---|---|---|---|---|
| 200 RPS | 200 | 3,2 мс | 8,9 мс | 46 мс | 0 % | ~66 % | 532 МБ |
| 300 RPS | 300 | 4,6 мс | 69 мс | 324 мс | 0 % | ~108 % | 394 МБ |
| 400 RPS | 400 | 6,4 мс | 94 мс | 251 мс | 0 % | ~126 % | 534 МБ |
| 600 RPS | 599 | 55 мс | 320 мс | 484 мс | 0 % | ~176 % | 536 МБ |
| 800 RPS | 687 (предел) | 1,49 с | 1,74 с | 1,86 с | 0 %* | ~200 % | - |

\* В прогоне на 800 RPS было 3,7 % ответов 404 из-за ошибки в самом сценарии: запросы по остановкам другого маршрута. Сценарий исправлен, на остальных ступенях ошибок 0 %.

**Итог:** один контейнер с 2 vCPU держит **400 RPS с p95 ≈ 94 мс** и 0 % ошибок при загрузке CPU ~63 % от лимита. Это соответствует целям ТЗ: сотни RPS, p95 < 200–300 мс, CPU 60–80 %. Около 600 RPS p95 доходит до ~320 мс, CPU почти упирается в лимит. Предел - примерно 690 RPS. RAM стабильна (0,4–0,5 ГБ из 2 ГБ), swap не используется. Для большей нагрузки: `docker compose up --scale api=N`.

### 4 воркера uvicorn на тех же 2 vCPU

| Нагрузка | Факт RPS | p95 | CPU api |
|---|---|---|---|
| 400 RPS | 314 (предел) | > 1 с | ~191 % |
| 600 RPS | 380 | 3,4 с | ~191 % |

С 4 воркерами хуже: процессы конкурируют за 2 vCPU, у каждого свой кеш запросов. Поэтому в compose оставлен `WEB_CONCURRENCY=2`: число воркеров равно числу vCPU.

### Через nginx (фронтенд → api)

| Нагрузка | Факт RPS | p50 | p95 | CPU api |
|---|---|---|---|---|
| 400 RPS | 178–216 | 3,8–5,2 с | 6–8 с | ~192 % |

Через прокси пропускная способность пока в 2 раза ниже прямой. Заголовки и размер ответов одинаковые. Причина ещё не найдена: включение keepalive к api (`upstream` с `resolve`) результат не изменило. Возможно, влияет то, что k6, nginx и api делят CPU одного хоста Docker Desktop. Это следующий шаг оптимизации. Цифры для API как сервиса - таблица «напрямую».

### Прогон файла на модели (`POST /api/predict/batch`, через nginx)

| Файл | Строк | Время | Пик RAM api |
|---|---|---|---|
| CSV 112 МБ | 6,5 млн | 17,6 с | 0,63 ГБ |
| CSV 1,01 ГБ | 58,5 млн | 148 с (~400 тыс. строк/с) | 1,68 ГБ* |

Файл обрабатывается потоком:
- тело запроса идёт из nginx в api без промежуточной буферизации;
- CSV читается и пишется блоками по 16 МБ через pyarrow, разбор ключей идёт векторно в `pyarrow.compute`;
- ответ стримится обратно.

До переработки файл 112 МБ обрабатывался 45,7 с при пике 1,37 ГБ.

\* В пике на 1 ГБ, по всей видимости, в основном файловый кеш от временных файлов: вход 1 ГБ и результат 1,8 ГБ на диске контейнера. Рабочая память ограничена размером блока. На диске контейнера нужно примерно 3× размер входного файла (`PREDICT_TMP_DIR` задаёт другую папку).

**Что сделано для производительности:**
- прогноз лежит в памяти плотным массивом `маршрут × день × час`, и запрос сводится к срезу и сумме в numpy;
- LRU-кеш результатов по версии snapshot;
- ORJSON, GZip, `ETag` и 304, `Cache-Control`;
- snapshot перечитывается без остановки сервиса.
